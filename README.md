# P2P Sync

WindowsとiOS向けの独立P2P同期アプリ。手動設定した相手と、署名済みのファイル変更を相互TLSで交換する試験版です。

手動設定でCloudflareシグナリングとWebRTC経路を使用できます。2026-11-26に別回線のWindowsとiPhone 11で直接接続、手動・前景自動同期、中断後の再試行を確認しました。転送ファイルを端末から読み戻し、2 MiBと16 MiBのSHA-256一致を確認しています。試験条件と未検証のTURN・バックグラウンド動作は[実機検証メモ](NAT_POC.md)に記録しています。

iOS版には受信画面と、書き込みピア用の共有・配信画面があります。共有元はアプリの Documents/P2PShared で、Filesアプリからファイルを入れられます。書き込みピアの設定フォルダーを選び、新規・変更ファイルを手動登録し、同じ設定フォルダーの `direct.json` で他ピアの変更を取得して、アプリが前面にある間だけ配信します。取得は中断でき、保存済みチャンクは次回に再利用します。取得と登録・更新は配信を停止してから行います。書き込みピア画面では、共有元から消えたファイルの候補を確認し、選んだ削除を同期変更として記録できます。iOSの既存受信ファイルの更新・削除・移動は、内容の取得後にファイル調整下で反映する実装を追加し、CIでビルドを確認しています。iPhone 11では別回線での受信、前景での自動同期、中断後の再試行を確認しました。共有・配信画面など、その他のiOS機能は個別に検証が必要です。Filesから選んだ外部フォルダーの書き込み対象化と、画面ロック中の配信継続は未実装・未検証です。

Windows・iOSの同期画面は、同期後に未解決の競合候補を表示します。候補の名前、発行元ピアIDの短縮形、版番号、取得済み本体の容量を確認できます。削除候補と本体未取得の候補も区別します。48時間の履歴は、同じ内容の本体を一度だけ数えた保存容量と、未取得の本体数を表示します。WindowsとiOSの書き込みピア画面でも、保護中の共通原本と容量・待機中ピアを確認し、履歴の復元と削除、競合候補の採用を操作できます。復元と採用は新しい署名付き変更として記録し、候補が変わった場合は操作を拒否します。履歴を削除しても保護中の共通原本は保持します。

Windowsでは書き込みピアの履歴を個別または一覧から一括削除できます。選択後に履歴が変わった場合は削除を拒否します。履歴を削除しても、現在の版・別の履歴・復旧待ち操作・未同期ピアのために必要な原本は保持します。

WindowsとiOSの書き込みピア画面では、共有元から消えたファイルを一覧で確認し、選択したファイルの削除を同期変更として記録できます。対象はこの端末が最後に変更した競合のないファイルで、共有元と親フォルダーを開ける場合に限ります。実行時に表示時の版とファイル不在を再確認します。共有元の実ファイルはこの操作で削除しません。共有元の不在を自動的に削除イベントへ変える処理は今後の対応です。

WindowsとiOSでは同じ候補から移動後の実ファイルを選び、元のファイルIDを保った移動として記録できます。旧名が空き、移動先が共有元の内側にある場合に受け付けます。内容も変わっている場合は検証済みの新版を保存し、移動と更新を一つの署名付き変更として記録します。移動先の親フォルダーは必要に応じて共有へ登録します。移動先を新規ファイルとして登録する前に操作してください。共有元の実ファイルは移動しません。移動の自動検出は今後の対応です。

同期後は、その端末に保存された48時間以内の履歴も表示します。元のパス、容量、アーカイブ日時を確認できます。

## Windows x64

RustのMSVCツールチェーン、Visual StudioのC++ビルドツールとWindows SDK、.NET 10 SDKが必要です。

GitHub Actionsの「Test and build Windows client」を手動実行すると、Windows固有のRust試験とGUIビルドを行い、`P2PSync-Windows` にEXEとRust DLLをまとめて保存します。この成果物はフレームワーク依存で、実行するPCに.NET 10 Windows Desktop Runtimeが必要です。インストーラーとコード署名は未実装です。

```powershell
cargo test --locked --workspace
cargo build --locked --release
dotnet run --project windows/P2PSync.csproj -c Release
```

画面で接続設定のJSONと保存先フォルダーを選び、「同期を開始」を押します。「10 秒ごとに自動同期」を有効にする場合は、前回の同期完了から10秒後に次回の受信を開始します。最小化すると通知領域へ移り、自動同期を続けます。通知領域のメニューから画面を開く・同期する・終了する操作ができます。ウィンドウを閉じるとアプリは終了します。選んだ設定・保存先・自動同期の選択は次回起動時に復元します。

## 直接接続の試験設定

試験用の証明書・秘密鍵と接続設定は配信コマンドの `setup` で生成できます。WindowsはJSONを選択します。iOSはJSONと証明書類を入れたフォルダーを選択します。iOSのJSON名は `direct.json`、同期先はアプリのDocuments内の `P2PSync` です。iOSでは選んだ接続設定フォルダーと自動同期の設定を保存します。「自動同期」は画面を開いている間に10秒間隔で実行します。画面を離れたあともiOSがバックグラウンド更新を許可した時点で同期を試します。実行時刻はOSが決定します。同期中に画面を離れると、その回の同期を続けるための実行時間をiOSに要求します。期限切れの場合は通信の区切りで中止を試み、次回同期で保存済みのチャンクを再利用できます。

`setup` の末尾に読み取り専用ピア数と書き込みピア数を指定できます。例えば `1 2` は読み取り専用ピア1台と、個別の鍵・証明書を持つ書き込みピア2台を生成します。書き込み用フォルダーは `sender`、`writer-2` の順です。各ピアは自分の `server.json` で取得済みデータを配信できます。待受ポートは書き込みピア、読み取り専用ピアの順に指定値から連番になります。各フォルダーの `direct.json` には他の書き込み・読み取り専用ピアを最大9台まで接続候補として登録します。すべてのピアが同じIPアドレスで待ち受ける試験設定なので、別の端末へ配布するときは各候補のアドレスを実際の端末に合わせて変更してください。読み取り専用ピアで `catch-up` と `serve-peer` を使う場合も、そのピア自身の `server.json` を指定します。読み取り専用ピアによる変更イベントの発行は拒否されます。各端末に配布するのはその端末専用のフォルダーだけです。

|JSON項目|内容|
|---|---|
|`share`|共有IDを32桁の16進数で指定|
|`generation`|共有の世代番号。1以上|
|`members`|Ed25519公開鍵を64桁の16進数キーとし、値を `reader` または `writer` とするオブジェクト|
|`address`|配信ピアのIPアドレスとTCPポート|
|`server_name`|配信ピアの証明書に含まれる名前|
|`server_pin`|配信ピアの証明書DERのSHA-256を64桁の16進数で指定|
|`fallback_peers`|追加の接続先。各要素に `address`、`server_name`、`server_pin` と任意の `connect_timeout_ms`（100〜15000）を指定し、最大8件。各ピアは同じ共有・世代・メンバー設定を使用|
|`ca_der`、`certificate_der`、`private_key_der`|それぞれCA証明書、クライアント証明書、クライアント秘密鍵のDERファイル名。JSONからの相対パスを使用可能|
|`event_key`|確認の署名に使う受信側Ed25519秘密鍵の32バイトseed。対応する公開鍵は `members` の `reader` に登録。旧設定では省略可能|

受信側は追加の接続先も設定順に試し、イベントとファイルキャッシュを引き継ぎます。署名付き確認は接続できた各ピアへ送信します。`setup` が生成する追加候補は接続開始だけ1.5秒で打ち切り、接続後の通信は通常の15秒待機を使います。別のネットワークで必要なら `connect_timeout_ms` を変更できます。

鍵や接続設定は信頼できるローカルファイルを使用してください。接続先の登録と証明書発行の画面は未実装です。Windowsは、同期先で反映済みの版と一致するファイルを更新・削除・移動できます。

### Windowsからの試験配信

同じPCで試す場合は、アクセス権を管理できる作業フォルダーで、まだ存在しない `trial-setup` を指定します。

```powershell
cargo run --locked --release -p p2p-sync-core --bin p2p-send -- setup .\trial-setup 127.0.0.1:8765 127.0.0.1:8765
```

`sender/server.json` と `receiver/direct.json` が生成されます。別端末で試すときは、受信端末から到達可能な配信PCのIPアドレスを、待受と接続先に指定してください。受信端末へ移すのは `receiver` フォルダーだけです。どちらにも秘密鍵があるため、公開フォルダーやGitに追加しないでください。試験証明書の有効期間は30日です。複数台で試す場合はsetupコマンドの末尾に台数（1〜32）を指定し、各受信端末に異なる receiver-N フォルダーを移します。

手動で設定する場合は、
受信設定と同じ `share`、`generation`、`members` を持つ `server.json` を用意します。配信には次のフィールドを指定します。

|JSON項目|内容|
|---|---|
|`bind`|TCP待受のアドレスとポート。同一PCでの試験は `127.0.0.1:8765`|
|`client_pin`|受信側証明書DERのSHA-256を64桁の16進数で指定。複数台の場合は client_pins 配列を指定|
|`client_identities`|端末の署名公開鍵64桁から証明書ピン64桁への対応表。`setup` が生成する。第2世代以降は必須で、ピン一覧と現在のメンバー表に一致することを起動時に検査|
|`ca_der`、`certificate_der`、`private_key_der`|CA証明書、配信側証明書、配信側秘密鍵のDERファイル名|
|`event_key`|配信側Ed25519秘密鍵の32バイトseedを保存したファイル。対応する公開鍵を `members` に `writer` として登録|

ルート直下に共有するファイルを登録してから配信を開始します。同じ状態フォルダーを両コマンドに渡します。停止はCtrl+Cです。

```powershell
cargo run --locked --release -p p2p-sync-core --bin p2p-send -- publish .\trial-setup\sender\server.json .\server-state .\song.tja
cargo run --locked --release -p p2p-sync-core --bin p2p-send -- serve .\trial-setup\sender\server.json .\server-state
```

現在は受信端末の証明書を事前登録する手動接続です。Windows GUIでは書き込みピア設定・状態フォルダー・共有元フォルダーを選び、共有元の新規・変更ファイルを登録し、設定ファイルと同じフォルダーの `direct.json` で他ピアの変更を手動取得して配信を開始・停止できます。取得は中断でき、保存済みチャンクは次回に再利用します。取得、登録・更新と履歴・競合の操作は配信を停止してから行います。共有元から消えたファイルは自動削除しません。設定ファイルや状態フォルダーを含む共有元は拒否します。画面を最小化しても配信を続け、トレイからも操作できます。GUIの配信は保持済みのイベントと本体を提供します。別ピアからの定期取得には `serve-peer` コマンドを使用します。

配信側と受信側は同じ共有ID・世代を設定し、両方のアプリを更新してください。共有ID・世代が異なる接続と、従来の世代照合を行わない接続方式は、TLS接続時に拒否されます。

同一世代の古いDBが復元された場合、世代別DBの外に残る署名済み変更イベントの証跡と照合します。削除や更新イベントがDBから消えていれば操作を止め、画面に状態復旧が必要と表示します。証跡だけが先行した途中終了も停止します。証跡はイベントごとに増えます。DBと証跡をまとめて古い状態へ戻す場合に備え、別の信頼済みピアが保持する署名付き履歴基準点を手動設定できます。配信側の起動時と受信側の同期開始前に照合します。登録済み基準点の自動更新と、設定で有効にした初回登録の自動化は実装済みです。すべての端末での設定強制、古い基底からの再初期同期、証跡の集約は未実装です。

配信側では、`p2p-send export-recovery-anchor <server.json> <state-dir> <new-output-file>`で署名付き履歴基準点を新規ファイルへ書き出せます。`p2p-send fetch-recovery-anchor <server.json> <state-dir> <direct.json> <trusted-peer-id> <new-output-file>`では、手動設定した主接続先から相互TLS経由で取得し、指定ピアの署名を検証して保存します。取得済みのファイルは上書きしません。初回の取得と配信設定への登録をまとめる場合は、履歴を相手に追いつかせてから`p2p-send register-recovery-anchor <server.json> <state-dir> <direct.json> <trusted-peer-id> <new-output-file>`を使えます。相手の署名付き基準点が現在の履歴と一致した場合だけ新しいファイルを書き、`server.json`へ登録します。検証失敗時は設定を変更しません。出力先は状態フォルダー外に指定します。受信側は、履歴を相手に追いつかせてから`p2p-send register-receiver-recovery-anchor <direct.json> <receiver-state-dir> <destination> <new-output-file>`で取得と登録をまとめて行えます。相手の署名と現在の履歴を照合し、失敗時は設定と出力を変更しません。出力先は状態フォルダーと共有先の外に指定します。登録後は`p2p-send refresh-receiver-recovery-anchor <direct.json> <receiver-state-dir> <destination>`で、相手の新しい基準点と履歴を非公開キャッシュへ取得し、古い基準点からの連続性を確認して更新できます。この操作は共有先のファイルを変更しません。登録済み基準点の署名者IDが主接続先の`event_peer`と一致する受信側では、通常同期の前にも同じ更新を自動実行します。主接続先に接続できず代替先がある場合は、既存の基準点を照合したうえで代替先との同期を続けます。別の信頼済みピアが保持した基準点を使う場合、配信側の`server.json`または受信側の`direct.json`に`"recovery_anchor":{"file":"../peer-anchor.bin","peer":"<署名したピアの公開鍵64桁>"}`を指定します。パスは各設定ファイルのフォルダー基準です。状態フォルダー内のファイルは基準点として拒否します。配信側は自分自身の署名も拒否します。配信側の起動時と配信する接続ごと、または受信側の同期開始前に履歴が基準点より古い、または分岐していれば処理を止めます。基準点は復元対象と独立した信頼済みピアから新しいものを受け取る必要があります。通信応答には毎回異なる乱数を署名して、以前の応答をそのまま再送する試みを拒否します。配信側も登録済み基準点がある場合、ピアからの履歴取得時に古い基準点と新しい基準点を照合して自動更新します。`serve-peer`の定期取得とWindows・iOSの共通ライブラリ経由の取得も対象です。初回基準点の自動登録は設定で有効にした端末だけで動作します。

初回登録を自動化する場合は、配信側の `server.json` または受信側の `direct.json` に `"auto_recovery_anchor":"../peer-anchor.bin"` を追加します。パスは設定ファイルのフォルダー基準で、状態フォルダー外、受信側では共有先の外に指定します。設定済みの主接続先の署名者IDを使い、配信側は履歴取得後、受信側は通常同期後に署名と現在の履歴を照合してから新規ファイルを作成し、設定に登録します。既存ファイルは上書きしません。初回登録で通信や照合が失敗した場合はエラーを返しますが、直前に取り込んだ履歴や同期済みファイルは残ります。再試行前に、出力ファイルが残っている場合は内容と設定を確認してください。

配信側で基準点より履歴が古くなって起動を拒否された場合、`p2p-send recover-from-anchor <server.json> <state-dir> <direct.json>`で署名済みイベントと検証済み本体を再取得できます。この専用コマンドは遅れた状態で共有元のスキャン・公開・配信や履歴整理を行わず、取り込み後に基準点を再照合します。履歴が分岐している場合は自動で上書きしません。復旧後は署名付き変更の発行を停止し、`p2p-send review-recovered-source <server.json> <state-dir> <folder>`で復旧履歴と実ファイルの差分を読み取り専用で一覧できます。履歴にあるのに共有元から消えたファイル・フォルダーも一覧に含め、確認するまで変更操作を再開しません。Windows・iOSアプリでも復旧後の差分一覧を見られ、差分がない場合は「変更操作を再開」で再確認できます。削除済みファイルや未送信の変更を別の場所へ保全するなどして共有元の差分を解消した後、`p2p-send resume-tree-refresh <server.json> <state-dir> <folder>`で変更操作を再開できます。再開時は正しい共有元フォルダーを指定してください。未送信変更を自動的に競合として取り込む機能はまだありません。

復旧後に共有元の未送信データを保全するには、`p2p-send archive-recovered-source <server.json> <state-dir> <folder> <new-output-dir>` を実行できます。履歴と異なる実ファイルを新規フォルダーの `source/` に複製し、SHA-256とサイズ、存在しない共有項目を `manifest.json` に記録します。出力先は共有元と状態フォルダーの外に指定し、既存の出力フォルダーは上書きしません。共有元と復旧後の変更停止状態は変えません。エラー時は出力フォルダーが途中まで残る場合があり、`manifest.json` がない場合は退避完了として扱いません。`p2p-send verify-recovered-source-archive <archive-dir>` で保存済みファイルのサイズとSHA-256を再照合できます。検証はマニフェストに記録されたファイルを対象とし、マニフェスト自体の独立した署名はありません。退避物を新しい同期履歴へ自動採用する機能はまだありません。

受信側が基準点より古い場合は、`p2p-send recover-receiver-from-anchor <direct.json> <receiver-state-dir> <destination>`で署名済みイベントと検証済み本体を受信側の非公開キャッシュへ再取得できます。Windows・iOSアプリにも「履歴だけを復旧」ボタンがあります。設定済みの外部基準点に追いつくまで通常同期は拒否されます。復旧処理は共有先のファイルを作成・更新・削除せず、基準点を再照合してから終了します。その後に通常の同期を実行してファイルへ反映します。受信側の設定には`event_key`が必要です。履歴が分岐している場合は復旧を拒否します。GUIの実機動作は未検証です。iOSでは保存済みの保留操作を反映する前に、主接続先の署名者IDに固定した登録済み基準点を取得・照合します。照合に失敗した場合は保留操作を反映しません。

基準点を設定済みの配信側では、`p2p-send refresh-recovery-anchor <server.json> <state-dir> <direct.json>`で相手から新しい基準点を取得し、イベントと本体を取り込んでから外部の基準点ファイルを更新できます。新旧双方の署名と履歴を照合し、候補が古い場合は元のファイルを残します。

`direct.json`の主接続先に`"event_peer":"<接続先の署名公開鍵64桁>"`を指定すると、同期開始時に相手から署名付き基準点を取得します。相手が自分で発行したイベントの履歴をこちらより古い状態へ戻していた場合、ファイルやイベントの取得前に接続を拒否します。`fallback_peers`の各接続先でも、それぞれの`event_peer`を指定できます。未指定の接続先では従来どおり同期します。新しく`setup`で作る接続設定には、主接続先とフォールバック先の公開鍵を自動記入します。このチェックだけで、両端末を同じ古い状態へ戻す場合は検出できません。

`p2p-send prepare-generation <server.json> <state-dir> <next-server.json> <administrator-seed-file> <new-dir>` で移行用データを作成できます。次の設定には同じ共有IDと1つ進んだ世代、新しいピア一覧を指定します。管理鍵には、同期ピアの署名鍵と別の32バイトのEd25519シードを使います。出力には署名済みの `transition.bin`、`checkpoint.bin`、検証済みの `files` が含まれます。出力フォルダーには共有ファイル本体が含まれるため、共有先と同様に管理してください。作成だけでは世代は切り替わりません。

`p2p-send verify-generation <previous-server.json> <next-server.json> <administrator-public-key> <bundle-dir>` は、信頼済みの管理公開鍵（Ed25519の生32バイト）を使って、署名、世代、ピア一覧、履歴、ファイル本体を検証します。検証は読み取り専用です。現段階のチェックポイント上限は128 MiBで、ファイル本体はこの上限に含みません。

新世代の配信・受信設定には `migration` を追加し、`previous_server`、`administrator_public_key`、`bundle` にそれぞれ旧世代のピア構成、信頼済みの管理公開鍵、検証済みの移行データのパスを指定します。パスは各設定ファイルからの相対パスを使えます。移行データは配信元・同期先・アプリのキャッシュ外に置き、再起動後も保持します。新世代へ移った端末同士は同じ署名済み移行データを使います。同じローカル保存領域では、有効化後の新しい配信・受信操作に新世代が必要になります。別の保存領域や、移行をまだ適用していない端末の旧世代セッションには影響しません。

ピアを登録解除する場合は、新世代の `members` から署名公開鍵を外し、各配信設定の `client_pin` または `client_pins` と `client_identities` から同ピアの証明書・対応付けも外します。現段階では手動で更新します。第2世代以降は証明書ピンの確認後、接続相手に毎回異なる値への署名を求め、対応表にある端末IDと一致するまで同期データを提供しません。読み取り専用端末の `direct.json` には `event_key` が必要です。旧世代の資格を持つ端末同士の通信や取得済みデータは取り消せません。

旧世代でオフライン中に行った編集は、アプリを閉じてから `p2p-send archive-isolated-generation <old-server.json> <old-state-dir> <next-server.json> <administrator-public-key> <bundle-dir> <new-output-dir>` で退避できます。退避先には旧DBの一貫した複製、チェックポイント後の署名済みイベント、検証済みのファイル本体、`report.json` を作成します。本体が既に欠けていればレポートに記録します。旧DBと共有元ファイルは変更しません。後から `p2p-send verify-isolated-archive <old-server.json> <next-server.json> <administrator-public-key> <bundle-dir> <archive-dir>` で署名・DB・本体・レポートを読み取り専用で再検証できます。新世代の `server.json` に `migration` が設定されていれば、WindowsとiOSの共有画面で退避フォルダーを選び、検証済みの編集一覧と欠落本体を表示できます。退避先には共有内容が含まれるため、公開フォルダーやGitに追加しないでください。編集の採用と新世代での再発行は自動化していません。

`p2p-send catch-up <server.json> <state-dir> <direct.json>` は、同じ共有・世代で登録された別の配信先から、署名付きイベントと取得可能なファイル本体を配信用キャッシュへ取り込みます。取り込んだデータは `serve` で再配信でき、作業フォルダーには書き込みません。接続には `direct.json` の主接続先と追加の接続先を設定順に使います。

同じ端末の受信状態にある署名付き確認を配信キャッシュへ取り込むには、`p2p-send import-confirmations <server.json> <server-state-dir> <direct.json> <receiver-state-dir> <destination>` を使います。`destination` は受信アプリが同期したフォルダーです。共有・世代と署名を検証し、配信キャッシュがまだ持たない変更イベントへの確認は次回の取り込みまで保留します。

`p2p-send serve-peer <server.json> <state-dir> <direct.json> <間隔秒> [receiver-state-dir destination]` は、配信しながら取り込みを繰り返します。末尾の2項目を指定すると、毎周期、同じ端末の受信状態から確認通知も取り込みます。接続に失敗した周期でもローカル通知の取り込みは試みます。間隔は1〜86400秒で、接続に失敗した場合も次の周期で再試行します。

配信側は、更新・削除から48時間を過ぎた旧版を、全登録ピアの確認がそろい、現行版・未解決の競合・期限内の履歴からも参照されなくなった時点で整理します。削除イベントは同期に必要なため保持します。同期接続では署名付きの反映確認を双方で交換し、中継ピア経由で元の配信元にも届けます。確認対象の変更イベントがまだ届いていないピアは確認を適用せず、次回接続で再送します。同じ端末の受信状態からCLIの配信キャッシュへの取り込みは、上記の `serve-peer` の引数を指定したときに定期実行します。

配信側の状態に競合がある場合は、`p2p-send conflicts <server.json> <state-dir>` で候補IDを確認できます。`p2p-send resolve <server.json> <state-dir> <採用する候補ID> <ほかの候補ID> ...` では、確認した候補をすべて指定します。候補が増減した場合は再確認が必要です。削除候補を採用すると共有上の削除を維持します。

`p2p-send history <server.json> <state-dir>` は48時間以内の履歴と、同じファイルの現在の版IDを表示します。`p2p-send restore <server.json> <state-dir> <archive-id> <reviewed-current-id>` は、選んだ履歴を新しい署名付き変更として復元します。確認した現在の版が変わった場合、競合中の場合、復元先に別の共有項目がある場合は保留します。ファイルIDを維持し、置き換える現在の内容も履歴へ保存します。Windows GUIからも復元できます。フォルダー自体の復元は今後の対応です。

譜面集をまとめて登録する場合は、`publish` の代わりに `publish-tree` を使います。

```powershell
cargo run --locked --release -p p2p-sync-core --bin p2p-send -- publish-tree .\trial-setup\sender\server.json .\server-state .\譜面集
```

指定フォルダー内の階層と空フォルダーも登録します。同じ内容の再登録は既存イベントを再利用します。

登録済みファイルを更新・削除・移動するには、共有内の相対パスをスラッシュ区切りで指定します。

```powershell
cargo run --locked --release -p p2p-sync-core --bin p2p-send -- update .\trial-setup\sender\server.json .\server-state '譜面/song.tja' .\最新版.tja
cargo run --locked --release -p p2p-sync-core --bin p2p-send -- delete .\trial-setup\sender\server.json .\server-state '譜面/song.tja'
cargo run --locked --release -p p2p-sync-core --bin p2p-send -- move .\trial-setup\sender\server.json .\server-state '譜面/song.tja' '譜面/renamed.tja'
```

各コマンドは共有上のイベントを記録します。配信時に指定した元ファイルは引き続きローカルに残ります。`move` は共有上のファイルIDと内容を維持し、既に共有に登録されたフォルダーへ移動できます。初回同期では移動後のパスに配置されます。Windowsの反映済みファイルは、内容が一致し、移動先が空いている場合に移動します。Windowsでは大文字・小文字だけが違う改名も反映します。Windowsでは移動と内容更新をまとめて受信した場合も反映します。iOSでの反映済みファイルの移動は保留になります。Windowsの受信側は、最後に反映した版と一致し、他のアプリが開いていない場合に更新・削除します。更新中は旧版を一時退避してから新版を配置し、途中停止時は次回同期で再開します。ローカルで変更済みのファイル、iOSでの更新・削除は保留と表示されます。

配信元フォルダーを再スキャンして同じパスの変更をまとめて送る場合は、`refresh-tree` を使います。新しいファイルは追加し、見つからないファイルは共有に残します。削除済みパスにファイルが残っている場合は、競合として報告します。

配信中に自動で再スキャンする場合は、末尾に間隔を秒で指定します。

```powershell
cargo run --locked --release -p p2p-sync-core --bin p2p-send -- serve-tree .\trial-setup\sender\server.json .\server-state .\譜面集 10
```

起動時と指定間隔で配信元を読み取り、追加と変更を登録します。設定・秘密鍵・配信状態のフォルダーは、共有するフォルダーの外に配置してください。
